# aure 性能优化指南

初始研究与源码核对日期：2026-10-05。用途：后续开发者或 AI 的实施依据；下文研究快照与方案预算不作为现行实测结果。

发现页已于 2026-10-06 改为按需最高 3072px 的高清缓存；下文原图节点复用属于研究时的源码快照，现行加载与预算见[大规模本地图库规范](../design/spec/06-large-library.md)。

2026-10-11 已在现有架构内实施页面按需加载、媒体视口索引、查询语句复用及后台缩略图清理。本文保留研究时的方案比较；当前机制、构建预算和可重复验证入口统一以[大规模本地图库规范](../design/spec/06-large-library.md)为准。`npm run verify` 统一检查构建、首屏依赖总量、发布体积和单元测试，不能将构建大小变化等同于启动时间提升。

## 1. 目标、证据与适用范围

目标规模为 **1000 套写真／10 万媒体**，压力档为 **5000 套／30 万媒体**。性能应围绕打开应用、查找写真、滚动、翻图和导入期间继续浏览衡量，不能只看批量处理速度。继续保留模特 → 写真集 → 媒体的浏览关系、连续浏览、有限查询窗口、关系完整性与原件保护。

本文标记四种证据：**源码确认**表示指定版本存在该机制；**官方说明**表示项目文档中的行为或建议；**实施建议**表示根据 aure 需求作出的推断；**实测结果**必须有环境、样本与计时依据。本次只有前三种，不提供项目速度排名或容量承诺。现行实施事实和预算以[大规模本地图库规范](../design/spec/06-large-library.md)为准，本文不重复维护实施状态。

当前主机只读核验为 Ultra 7 251HX、18 个逻辑处理器、约 15.7 GiB 内存。磁盘型号、原件所在卷、显示器分辨率与缩放未核验。CPU 核数不能直接变成解码并发数；开发工具和 WebView2 也共享内存。不得从这些参数推导性能保证。

## 2. 相似项目提供了哪些机制

| 项目与证据 | 观察到的机制 | 适用边界 |
| --- | --- | --- |
| Lap，源码确认 | 可见范围分块加载；当前视口优先，再取下方、上方；批量缩略图请求与分类后台预算。[加载][lap-load]、[队列][lap-thumb]、[预算][lap-budget] | 同为 Tauri，但 Vue 与 React 不同；不移植它的参数或大型组件 |
| Immich，官方说明 | 分离小缩略图、大预览与模糊占位；任务并发主要改善吞吐量，过高可能影响请求响应。[系统设置][immich] | 服务端任务与桌面前台的资源竞争不同，不引入其服务端部署体系 |
| PhotoPrism，官方说明 | 分页渐进追加；屏外卡片用轻量占位替换；多尺寸派生图按用途预生成或按需生成。[滚动][pp-scroll]、[派生图][pp-thumb] | 占位节点及已取数据仍可能累积，不能理解为完整内存常量化 |
| digiKam，官方说明 | 数据库和缩略图靠近本机；新文件扫描在后台，启动扫描仍可能拖慢初始化。[数据库][dk-db]、[扫描][dk-scan] | Qt 原生界面经验可借鉴，不能据其规模建议判定 aure 必须换数据库 |
| nomacs，源码确认 | 当前图加载后触发邻图缓存；下一张可在线程中加载，较远图片可预取文件；数量与缓存内存参与判断。[加载器][nomacs] | 缓存预算没有把当前与上一张纳入同一检查；不能当作进程严格上限 |

这些机制分别控制数据、节点、像素与后台竞争，需作为完整链路配合。Lap 的几何预处理仍遍历布局数据；nomacs 的缓存更新也遍历目录项，成熟项目并非所有操作都有常量成本。

## 3. 研究时的源码基础与边界

以下为 2026-10-05 的源码研究快照，不等同于当前能力或桌面验收。特别是首页原图缓存、512px 单档、同步清理等记录已有后续实现取代；新任务先核对现行性能规范与源码，不按本表重建旧方案：

| 链路 | 当前能力 | 不能据此宣称 |
| --- | --- | --- |
| 数据 | SQLite WAL、事务、索引；列表最多 96 项，候选最多 48 项；局部差量写入。[适配层](../src/infrastructure/desktop-repository.ts)、[数据库](../src-tauri/src/catalog/mod.rs) | 每个查询都快；DTO 中封面、预览等关联记录总数也只有 96 |
| 渲染 | 超过 48 项启用虚拟网格；缓冲两行，保留焦点附近行；图片在视口附近请求。[网格](../src/ui/VirtualGrid.tsx)、[图片](../src/ui/Photo.tsx) | 图片解码、React 更新、布局测量也自动消失 |
| 缩略图 | 来源去重、优先级、订阅取消；前端并发 2，最多 256 个任务，含运行项；原生生成并发 2、最长边 512。[前端](../src/infrastructure/thumbnail-service.ts)、[原生](../src-tauri/src/thumbnails.rs) | 所有业务都正确使用优先级；取消能中止已经运行的原生解码 |
| 原图 | 稳定媒体 ID、精确授权及资源协议；查看器挂载当前原图，视频按范围读取。[资源](../src-tauri/src/catalog/mod.rs)、[查看器](../src/features/viewer/Viewer.tsx) | 全部图片／编码都能播放；目前已实现邻图预加载 |
| 首页 | 保留最多五个已加载原图节点，按预计 RGBA 像素量限制为 512 MiB；资源版本与条件请求减少重复加载。[节点缓存](../src/infrastructure/original-cover-cache.ts) | 正在显示的图片、解码中间缓冲、GPU 和全部 WebView2 进程也受此上限约束 |
| 导入／缓存 | 单层扫描跳过链接；登记与业务保存事务提交。缓存按 512 MiB／10 万文件管理，首次请求和每 32 次生成清理。[扫描](../src-tauri/src/importing.rs)、[缓存](../src-tauri/src/thumbnails.rs) | 已有持续文件监听；磁盘淘汰是 LRU；已有十万真实文件长时间验收 |

`useData().db` 是页面快照，不能拿数组长度统计全库，更不能整库覆盖写回。磁盘缓存按文件修改时间淘汰；首页节点缓存按最近使用保留，两者不是同一种策略。

## 4. 六条链路的优化方法

本节全部是实施建议。每项先采样定位，确认瓶颈后再执行。

### 4.1 启动与查询：先取得可用页面

启动只取得当前页面及必要摘要，不把整库扫描、缓存维护或完整关系读取串到首屏之前。digiKam 的后台扫描提示：工作移到后台仍会竞争磁盘，不能只判断是否阻塞 UI 线程。[扫描说明][dk-scan]

把查询拆为连接等待、SQL、DTO 序列化、IPC 和前端提交，分别计时。aure 当前连接由互斥锁保护，后台写入可能使读取排队。先用 `EXPLAIN QUERY PLAN` 查筛选、排序、关联和计数是否利用合适索引，再评估事务长度；WAL 不会绕过应用自己的锁。[SQLite 查询计划][sqlite-eqp]

保留稳定次级排序键。深页 `OFFSET`、总数聚合或子串搜索只有在压力档确实变慢时才优化：顺序浏览可评估游标，随机跳页要保留定位能力；中文搜索需先定义匹配语义，不能为引入 FTS 改掉原有行为。收益是减少等待，代价是索引写入和接口复杂度；回退到原查询。验收覆盖首、中、末页及稀疏／高命中搜索，核对数量和排序。

### 4.2 列表滚动：控制节点，也控制附带工作

懒加载只推迟图片，不限制卡片数量。PhotoPrism 的屏外占位减少完整卡片成本；aure 已有虚拟网格，应优先检查滚动时的测量、父级更新和卡片附带查询，不更换布局体系。[滚动机制][pp-scroll]

可见项先加载，缓冲区次之，预取最低；快速滚动移除无订阅的等待任务，页面切换拒绝旧结果。把预取限制在当前页和邻近视口，不跨整库追加。稳定 ID 保持选择、焦点和返回位置；详情全选仍明确为本页。

只对采样显示昂贵的摘要、格式化和重复渲染做缓存，避免为所有对象维护永久索引。收益是降低每帧工作，代价是失效逻辑和少量缓冲内存。验收向下／反向滚动、连续翻页、筛选后返回及键盘操作，记录 DOM、图片节点和长任务；缓冲变大导致资源竞争时退回现有两行。

### 4.3 缩略图：按显示像素分层

照片数量影响查询，像素尺寸影响解码。一张 6000×4000 图的 RGBA 像素约 91.6 MiB；512×512 约 1 MiB。这是像素估算，不是 JPEG 磁盘大小，也不是进程完整内存。Immich 分离缩略图和预览；PhotoPrism 提供用途不同的派生尺寸。[图像设置][immich]、[尺寸表][pp-thumb]

保留现有 512 档作基线，以实际显示尺寸×设备像素比选择最低足够档位。建议试验 512／1024 的列表档及 2048／3072 的预览档，禁止放大小原件；这些是试验候选，尚未验收，不要求为每张预生成全部档位。

首页重点使用高质量预览，维持现有裁切与视觉构图。`object-fit: cover` 时须按等比缩放后的完整图需求计算像素，不能只用容器最长边；窄竖图填宽容器尤其容易低估。缩放后按肤色、发丝、衣料、暗部、锐度和色彩与原图对比。保持方向和正确色彩转换，避免简单丢弃 ICC 造成偏色；预览通过后才替换首页原图路径。

现有 JPEG 编码链路先作为基线，压缩格式和质量一起测编码时间、文件大小、呈现延迟与视觉效果，再决定是否新增依赖。收益是少读、少解码；代价是生成和磁盘空间。验收低／高像素比、窗口变化及宽窄构图，失败时保留当前首页原图策略，普通列表继续占位重试，不回退原图。

### 4.4 大图浏览：先呈现，再按需取得细节

首张使用足够覆盖屏幕的预览，放大超过预览细节能力时取原图；切换时保持缩放、中心和方向一致，不短暂串到另一张。原图不可用须明确反馈，不能让低清预览冒充原图。

借鉴 nomacs 的邻图准备，先试验只预取下一张预览；当前图显示完成且交互空闲后再开始。反向浏览改变预取方向；快速跳转丢弃旧结果并释放无用资源。当前原图之外默认不解码邻图原件，大尺寸或预算不足时停止预取。[邻图缓存][nomacs]

区分缓存压缩字节与保留解码节点；移除引用不代表浏览器立即释放 GPU 或进程内存。收益是减少翻图等待，代价是额外读盘及缓存；无收益或内存增长时关闭预取。图片／视频切换暂停并卸载旧播放资源；视频维持范围读取，不缓存整段，不自动转码原件。验收快速连按、反向、缩放、坏图及视频 seek，并检查原件哈希不变。

### 4.5 导入与后台任务：吞吐量服从浏览响应

导入的登记事务与派生图生成分开，不能每完成一张就重写整库。当前资料和关联的原子保存语义保持；只有测量发现事务阻塞，才研究后台分批登记，并明确恢复和提交边界。

Lap 将普通、重型缩略图与特征处理分开；PhotoPrism 的官方调优也限制工作者以避免竞争。[预算][lap-budget]、[调优][pp-perf] aure 先保留并发 2，再试验“当前浏览优先、后台预热暂停或降为 1”的调度。不能简单把各类任务并发相加；还需共享解码像素和磁盘预算。

将来增量扫描按登记信息比较大小、修改时间，只对变化项重新取元数据；这种比较不是内容一致性的严格证明。扫描取消、外接盘离线或遍历失败不等于文件被删除，不能清理关联。先提供显式刷新，再按需求研究监听与事件合并，避免启动全盘遍历。

收益是导入期间可继续操作，代价是后台完成更慢及恢复逻辑。验收导入同时搜索／滚动、重复导入、取消和离线；调度不稳定时回到现有按需生成，保留已提交的数据。

### 4.6 缓存维护：限制存储，不在关键路径反复扫目录

若平均每张缩略图 20 KiB，10 万张约 1.9 GiB，已超过现有 512 MiB 磁盘预算；文件数量上限不能代表所有图都会常驻。这是容量演算，不是实际平均大小。加入高质量预览后应分别统计各档命中、生成与淘汰，识别重复生成造成的抖动。

aure 当前清理遍历专用目录、读取元数据并排序，成本随缓存文件数增长，可能影响首次请求或生成返回；这是待测风险。先记录清理耗时、文件数和队列等待，确认后才改为后台限时／分批清理，必要时增加可重建的缓存索引，避免每 32 次生成进行完整维护。

指纹继续包括来源版本、尺寸、生成算法版本；访问仍核对授权，不因命中跳过路径保护。多尺寸共用总磁盘预算，旧档按需失效，不清空用户数据。清理只触及专用派生目录，忽略链接；保护运行中的写入与正在服务的资源，缺失缓存允许重建。

收益是压低维护延迟，代价是索引一致性和临时超额。验收预算触发、重启、文件修改、缓存缺失与同时读取；维护失败报告独立状态，不阻断全部浏览。可退回旧缓存目录与规则，但不能把它当作性能已满足的证明。

## 5. 后续接口需要的最小能力

以下不是已经实现的 API，也不要求本次迁移 schema。沿用 Repository／平台适配边界，UI 不直接调用 SQL 或处理文件路径。

| 能力 | 后续设计应表达的内容 |
| --- | --- |
| 派生图请求 | 稳定媒体 ID、用途／尺寸档；返回资源 URL、实际尺寸、来源版本；区分生成中、不可用与可重试 |
| 任务调度 | 优先级、订阅取消、排队／运行／完成／失败；取消等待与中断解码分别表达 |
| 版本保护 | 页面查询版本防旧响应；来源版本使各档同时失效；尺寸及算法版本进入缓存键 |
| 性能记录 | 请求关联 ID、阶段时间、队列长度、缓存层命中和失败原因；默认不记录私人文件路径 |

优先扩展现有服务，避免透传包装或引入 Redis、服务端数据库、分布式队列。详细字段、持久化任务和迁移仅在对应功能实施前确定。

## 6. 实施顺序与回退

| 优先级 | 工作及启动条件 | 收益／成本 | 回退 |
| --- | --- | --- | --- |
| P0 | 统一计时与真实样本；所有优化之前 | 确定瓶颈；增加少量测量工作 | 关闭测量，不影响业务 |
| P1 | 首页高质量预览；原图读盘／解码占主导且画质通过 | 降低首屏成本；新增派生档 | 恢复当前原图与节点复用 |
| P1 | 查看器屏幕预览及单张邻图预取；翻图等待明显 | 改善呈现；消耗额外缓存 | 关闭预取，保留当前图加载 |
| P2 | 调度和缓存维护；后台竞争／清理已被测出 | 降低峰值等待；后台吞吐可能下降 | 原并发与按需生成 |
| 条件项 | 查询索引、分页或搜索；数据库阶段超过预算 | 改善查询；增加维护／兼容成本 | 旧查询及分页语义 |

每项独立比较，不能同时改尺寸、格式、并发和分页后把收益归因于其中一项。保留数据恢复途径，不用重置图库消除回归。优化实施另开任务，完成后才更新现行性能规范。

## 7. 测量与验收矩阵

先用小型真实样本确认功能，再跑目标档与压力档的合成元数据；真实媒体另用可丢弃、已授权样本。记录尺寸、格式、文件大小分布及原件所在盘。只有确实准备了十万真实文件，才能报告相应实测；重复引用少量图片不等同于真实文件压力。

统一使用 Windows **Release WebView2**，浏览器测试只验证自身范围。记录应用哈希、系统与 WebView2 版本、CPU／内存、盘与显示条件，以及无后台／后台生成两档。正式图库仅只读；所有写入使用独立 identifier、数据库和缓存。

| 指标 | 定义与采样 | 判定 |
| --- | --- | --- |
| 首屏可交互 | 外部启动进程时间 → 目标首屏卡片提交、必要事件可响应；另记首张清晰封面呈现 | 现有参考预算 3 秒；首次迁移另计 |
| 搜索 P95 | 输入确定／防抖结束 → 正确结果提交；另记 SQL、锁等待与 IPC | 现有参考预算 200 ms；20 个固定查询，各重复 5 次，排序取第 95 个；冷／热分开 |
| 图片呈现 | 切换输入 → 正确图片解码完成、提交后两个动画帧；分别记预览和原图 | 待建立预算；这是呈现近似，不是精确屏幕扫描时间 |
| 滚动／长任务 | 固定滚动路径和窗口尺寸；记录超过 50 ms 的主线程任务、帧间隔及节点峰值 | 50 ms 为采样阈值，非“允许卡顿”；无全库规模增长的节点累积 |
| 排队／命中 | 入队 → 开始执行；区分磁盘、节点复用及 HTTP 304，记录各自分母 | 新预算待测；304 不证明避免了解码 |
| 内存趋势 | JS 堆、应用及所属 WebView2 进程私有内存／工作集分列，记录 GPU 可得指标 | 不能只看 JS 堆；长时复访不持续无界增长 |

现有[重启脚本](../tests/native/native-restart.mjs)记录暖 OS 缓存／已有 WebView 配置，启动时间戳缺失时为 `null`；不能改名为严格冷启动成绩。区分进程冷启动、派生缓存空／热、OS 缓存状态，无法控制时注明“未知”，不清理正式缓存。建议 5 次独立启动和至少 30 分钟稳定性采样，属于本指南测试方案，尚未执行。
